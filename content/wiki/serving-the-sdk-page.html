Your integration works when you double-click it. This is the next question: getting it onto a web address other people can open. Sometimes called hosting, sometimes serving — the same job either way.

You do not need this to get a stream running

Set up the Web SDK ends with the page working from your own disk. Come here when you want somebody else to be able to open it.

Why file:// stops being good enough

Opening the page from disk works today, and it is the quickest way to see a stream. It is not something to build on, for two reasons:

  • It relies on a policy you do not control. It works because the token endpoint sends Access-Control-Allow-Origin: *, which accepts the null origin a file:// page has. That is a server-side decision, and you would not be told if it changed.
  • It is not how your integration will run. A problem that only appears over http:// is better found now than after you have moved the files into your real application.

The quickest way to serve it locally

Any static file server will do. The SDK is plain HTML and JavaScript, so there is nothing to compile and no runtime to install. 

python -m http.server 8000     # Python 3
npx serve .                    # Node.js
php -S localhost:8000          # PHP

Then open http://localhost:8000. Nothing about the configuration changes.

Putting it on a real address

Once it works over http:// locally, publishing it is an ordinary static-site job. The SDK does not constrain the choice:

OptionWorth knowing
Your own web server — nginx, Apache, IIS Copy the folder into the document root. No application server, no Node process.
Static hosting or a CDN Works, because there is nothing dynamic to run. Good if the page is mostly the stream.
Inside an application you already have The usual end state — the SDK files become part of a page your framework already serves.

A public address changes one thing, and it matters

As soon as the page is reachable by other people, the API key in sdk-config.js is reachable too — it is one click of View Source away, and it does not expire.

Do this before you publish, not after: keeping the API key off the browser. It is one change to one function and nothing else in your integration moves.

Your own domain is not a problem

The SDK does not require the page to be served from an Eagle 3D Streaming domain. The demo is the proof: it runs on eaglepixelstreaming.com and streams from connector.eagle3dstreaming.com — two different origins. Your page can live on your own domain, behind your own login.

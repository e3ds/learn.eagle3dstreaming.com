A stream captures whichever microphone the operating system calls the default. Two commands let your own page offer the viewer a proper picker and switch the device mid-session, without dropping the stream.

Without this, the only way a viewer can change input device is the browser's padlock menu or the operating system's sound settings. For anyone who is not comfortable in browser settings that may as well not exist — so the picker belongs on your page, where your users already are.

This is an iframe feature. An SDK page shares a document with the player and does not hit either of the two walls below, so the SDK has no equivalent call today. If you need one, ask — the implementation already exists.

Why your page cannot do this itself

It is worth seeing the two walls before the commands make sense. Both come from the same thing: the stream runs in an iframe on a different origin.

WallWhat it meansThe command that solves it
A deviceId is scoped to the origin that produced it Ids your page collects are meaningless inside the frame getMicDevices — the list must come from in there
The iframe is cross-origin Your page cannot reach the MediaStream or the peer connection at all setMicDevice — the swap must happen in there

Reloading the iframe is not a workaround. It tears down the WebRTC session, puts the viewer back in the queue, and still lands on the system default device. It costs a session and does not even work.

The order things have to happen in

This is the part that catches people. You cannot get a useful device list before the browser has granted the microphone, and the browser only grants it when something asks — which the player does when the session connects, not when your page loads.

What happens if you ask too early

Neither command throws. Both answer — and the answer tells you which wall you hit, which is why it is worth reading rather than ignoring.

An empty label is not an error. Browsers withhold device names until the microphone has been granted once. The devices are real and their ids work; the names appear the moment permission is given. Number them and say so, rather than rendering a column of blank rows.

Reading the reply

error carries the browser's own error name, because the cases call for four different messages on your side.

errorWhat happenedWhat to tell the viewer
NotAllowedError The viewer has refused the microphone for this site "Allow the microphone in the padlock menu beside the address bar." Nothing on the page can override this.
OverconstrainedError The chosen device is no longer there "That microphone was disconnected." Re-list and let them pick again.
NotFoundError There is no matching input device Re-list.
NotReadableError The device exists but another application has it "Close whatever else is using the microphone and try again."
no audio sender… There is no audio track on the connection to swap You asked before the session was up, or the app is not configured with Enable Browser Microphone.

On success you get back the deviceId as the browser resolved it, plus the device's label — so your picker can confirm what it actually got rather than what it asked for.

Switching does not restart the stream

     before                setMicDevice              after
  +------------+                                 +------------+
  | RTCPeerConn|                                 | RTCPeerConn|
  |  +------+  |    sender.replaceTrack(new)     |  +------+  |
  |  |sender|--+--> default mic  ==========>     |  |sender|--+--> chosen mic
  |  +------+  |                                 |  +------+  |
  +------------+     no renegotiation            +------------+
                     no re-queue
   same session ------ no reconnect ------------> same session

replaceTrack() swaps the outgoing track on an established sender without renegotiating, so the call continues uninterrupted. The old track is stopped after the new one is acquired and swapped in — any other order means a device that has been unplugged since the list was built costs the viewer the microphone they still had.

Devices appearing and disappearing

The player watches the browser's devicechange event and re-sends micDevices on its own when the machine's inputs change. Plug in a headset mid-session and your picker refreshes without anyone pressing anything.

So micDevices can arrive unprompted. Handle it as "here is the current list", not as "here is the answer to the question you just asked".

The whole exchange

DirectionMessage
page → frame{ cmd: "getMicDevices" }
frame → page{ type: "micDevices", ok: true, devices: [{ deviceId, label, isActive }] }
page → frame{ cmd: "setMicDevice", deviceId: "<id from micDevices>" }
frame → page{ type: "micDeviceChanged", ok: true, deviceId, label }
frame → page{ type: "micDeviceChanged", ok: false, error, message }

A working page

const frame = document.getElementById("streamFrame");

function send(message) {
  frame.contentWindow.postMessage(JSON.stringify(message), "*");
}

window.addEventListener("message", (event) => {
  const data = event.data;
  if (!data || !data.type) return;

  // Build the controls only once the video is playing - before that the
  // labels are empty and there is no track to swap.
  if (data.type === "stream.playing") {
    send({ cmd: "getMicDevices" });
  }

  // Can also arrive unprompted, when a device is plugged in or removed.
  if (data.type === "micDevices") {
    const select = document.getElementById("micPicker");
    select.innerHTML = "";
    data.devices.forEach((device, i) => {
      const option = document.createElement("option");
      option.value = device.deviceId;
      option.textContent = device.label || `Microphone ${i + 1}`;
      option.selected = device.isActive;
      select.appendChild(option);
    });
  }

  if (data.type === "micDeviceChanged") {
    if (data.ok) showStatus(`Now using ${data.label}`);
    else showStatus(describe(data.error));
  }
});

document.getElementById("micPicker").addEventListener("change", (e) => {
  send({ cmd: "setMicDevice", deviceId: e.target.value });
});

Before any of this works

RequirementWhere
The <iframe> carries allow="microphone" Your page's HTML. Read only when the frame's document loads — changing it later means reassigning src.
Enable Browser Microphone is on The app's configuration in the Control Panel. Without it there is no audio sender to swap a track on.
The viewer allows the microphone when asked The browser. If they refuse, only they can undo it.

allow is not the same as permission. The attribute says whether your page is willing to share the microphone with the frame. It does not decide whether the browser will grant it — that is the viewer's own choice for your site. The two failures look identical from the outside, so show the browser's current answer next to your picker: navigator.permissions.query({ name: "microphone" }).

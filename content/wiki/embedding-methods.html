There are three ways to put an Eagle 3D Streaming session in front of someone. They differ in how much you build and how much control you get — but nearly every feature is available in all three. Pick a task on the left, then compare the three methods.

The three methods

Nothing to build

The streaming URL

We host the page. You send people a link. The controls are the ones you switch on in your configuration.

Host one page

iframe

Your page, your address, our player inside a frame. You talk to it by posting messages.

Host a page, and ideally a server

JavaScript SDK

Our player rendered directly in your page, driven by JavaScript calls. You own the session.

All three run the same thing

Underneath, every method is the same Pixel Streaming session on the same machine, reached through the same connector. The iframe and the SDK are thin layers over the player we already serve at the streaming URL — so moving between them changes your integration code, never your Unreal application.

The security difference is access control, not secrecy

An iframe needs no key, which sounds safer — but the streaming URL inside it is a bearer credential: anyone who finds it can stream, and you cannot revoke it for one person. With the SDK, the session starts from a token your own server issues, so your code decides who gets one and on what terms. The API key is the cost of that, and keeping it on the server is what makes the trade worth taking.

Start with the URL, move when something forces you to. The usual path is: send the link while you are proving the app works; move to an iframe when you want your own address and your own page around it; move to the SDK when you need to decide who may stream, or need a control the iframe does not expose. Nothing in your Unreal project changes at either step.

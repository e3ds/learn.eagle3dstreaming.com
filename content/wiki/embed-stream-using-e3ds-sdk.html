You have most likely already opened the demo, seen what it does, and decided the Web SDK is how you want to embed your application. If so, this is the page for you: get the code, point it at your app, and run it.

If you have not tried it yet, do that first

The Web SDK demo manual walks through the running demo control by control, with nothing to download and no key to enter. It is a much cheaper way to find out whether this is the right method for you than reading the rest of this page.

While you were there you may have noticed the demo runs on eaglepixelstreaming.com while the platform it streams from is connector.eagle3dstreaming.com. Different origins. That is deliberate — it is the answer to "will this work on my own domain?", demonstrated rather than promised.

Get the source code

github.com/e3ds/pixelstreaming-sdk — the source code of the demo you just used. Not a cut-down sample: it is the same code, running.

Get it streaming your app before you move anything into your own web project. It is a working integration, so anything that fails is your configuration rather than your code — a far smaller thing to debug than both at once.

What is in it

index.html                       the page itself
css/style.css                    styles the demo's buttons only
scripts/
├── sdk-config.js                the only file you must edit
├── sdk-token.js                 gets a token, starts the session
├── sdk-callbacks.js             every callback, documented
├── demo-ui-controls.js          the demo's buttons
├── demo-ui-connection-setup.js  the demo's settings dialog
└── dist/e3dsCore.min_ns.js      the SDK itself (generated, never edit)

sdk-* is the integration — those files, plus dist/, are what goes into your own web project. You can write your own from scratch against the same API, but copying these across is the quicker path and they are already correct.

demo-ui-* is the demo wrapped around it, and css/style.css styles only those buttons. If you are building your own interface you need none of the three.

Read demo-ui-controls.js before you build your own interface

You will delete it, but read it first. It is a worked example of driving every part of the SDK — building controls, wiring them to calls, and knowing when each one is safe to show.

That last part is not obvious and is easy to get wrong: some controls need only a session, others need the data channel open, and a button offered too early looks broken to the person clicking it.

Configure it

Everything you change is in scripts/sdk-config.js. It is the only file you have to edit.

What you must set

SettingSet it to
STREAMING_API_KEY Your Streaming API key — see below.
application.userName The account that owns the app.
application.appName The app's name, exactly as the Control Panel shows it, capitalisation included.
application.configurationName Which stored configuration to launch.

What you can leave alone

SettingDefault, and when to change it
application.version "latest" uses the newest build. Set a specific version only when you need to pin one.
application.domain connector.eagle3dstreaming.com for everyone on our platform. Enterprise only — see below.
tokenExpiryMs 60000. The token only has to last long enough to start the session.
configurationToOverride Empty. Per-session overrides of the stored configuration; it does not change the saved one.

The account API key will not work here

There are two credentials in the Developer section and they are not alternatives. Only the Streaming API key works with the SDK. The account API key is for the Control Panel APIs; used here it fails at token generation, with nothing in the error that says "wrong sort of key".

Read Streaming API key and tokens to understand the difference — which is which, where each lives in the Control Panel, and what the Streaming key produces.

application.domain is for enterprise plans

On our platform it is connector.eagle3dstreaming.com and you do not need to think about it.

If you have a custom system streaming dedicated to you, under the enterprise plan, it has its own domain and that is what goes here. You are normally given it when the system is handed over — if you have one and do not know your domain, ask support rather than guessing. A wrong domain fails at connection time and looks like a network fault.

There is one username, and it is application.userName

It says whose app to launch, and it is the name the session is recorded against. The token request carries it twice — once inside the application block, once beside it under the API's own name, client — but sdk-token.js fills in both from the one field, so there is nothing to keep in step.

Keep it stable for the life of a session. The token is looked up afterwards by the value it was created with, so a value that changes in between makes verification answer 404 for a token that is perfectly good — a failure that reads as expiry and is not.

Came from an older sample? Delete clientUserName

sdk-config.js used to carry a second field, clientUserName, described as "who is watching". It always held the same value as application.userName — the demo set both to the same string — so it was removed in SDK 4.23, and the sample reads the one that is left. An older config with both in it still works; the extra field is simply ignored.

Run it

Double-click index.html. That is the step — no server, no build, no install. The stream starts by itself. Press F12 to watch the session progress in the console.

Opening it straight from disk works because the token endpoint sends Access-Control-Allow-Origin: *, which accepts the null origin a file:// page has.

Your application is now streaming on your own machine, from a file on your disk. No server was involved, and nothing was uploaded.

Script order is not arbitrary

<script defer src="./scripts/dist/e3dsCore.min_ns.js"></script>
<script defer src="./scripts/sdk-config.js"></script>
<script defer src="./scripts/sdk-callbacks.js"></script>
<script defer src="./scripts/demo-ui-controls.js"></script>
<script defer src="./scripts/sdk-token.js"></script>

Two rules, and breaking one of them fails silently

The SDK loads first. The SDK is dist/e3dsCore.min_ns.js — that one file is the whole of it, and it is what defines e3ds_controller. Everything after it refers to that object, so move it and you get e3ds_controller is not defined — which at least says so.

sdk-token.js loads last, because it is the file that starts the stream: it holds the API call that exchanges your key for a session token and hands that token to the player's main function. A callback registered after the stream has started has already missed whatever fired first. That one produces no error at all — just callbacks that never run.

Moving it into your own application

Carry sdk-config.js, sdk-token.js, sdk-callbacks.js and dist/ across. Leave demo-ui-* and css/style.css behind — they are the demo's interface, and you are writing your own.

When you are ready for other people to open it, that is the next job: serving the page.

Upgrading from the SDK we shipped before 2026

If you are here because an existing integration stopped working: the streaming infrastructure was upgraded and the previous SDK is not compatible with it. Integrations still on it have stopped streaming rather than degraded.

Nothing changes in your Unreal application. The work is entirely on the web side, which makes the move smaller than it sounds — the steps above are the whole of it.

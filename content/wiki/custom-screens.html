Replace our loading, session-expired and crash screens with your own, so a wait or a failure looks like your product rather than ours.

All three work the same way: the platform tells your page what is happening, and you decide what to show. With the SDK that is a callback; with an iframe it is a postMessage event.

A loading screen

Two events bracket the wait, and the pattern is just show-then-hide:

EventWhat to do
onConfigAcquireShow your loading screen — the session is preparing.
onDataChannelOpenHide it — the stream is live.
 
e3ds_controller.callbacks.onConfigAcquire = function () {
  document.getElementById("myLoadingScreen").style.display = "flex";
};

e3ds_controller.callbacks.onDataChannelOpen = function () {
  document.getElementById("myLoadingScreen").style.display = "none";
};

For a progress bar rather than a static image, the three onReceivingApp…Progress callbacks report acquiring, preparing and starting as they happen.

If you use a hosted image, use the direct image URL — the one ending in .png or .jpg, not the page the host shows you. A share page will not load as an image, and the failure is silent: an empty loading screen rather than an error.

A session-expired screen

By default the platform shows its own "session expired" page. To show yours instead: 

e3ds_controller.callbacks.onSessionExpired = function () {
  document.getElementById("mySessionEnded").style.display = "flex";
};

With an iframe, keep a full-screen overlay hidden in your page and reveal it when the frame reports the session has ended. Since the overlay is yours, you can put a "start a new session" button on it — which the default screen does not offer.

onSessionExpired only covers the time limit. It does not fire for a crash, an idle timeout, a wrong password or an expired link. If you want one screen for every way a session can end, build it on onSessionEnding instead — that one fires for all of them and carries a line of text explaining which.

A crash-only message

Showing "something went wrong" when a session simply timed out is worse than showing nothing. To react to a genuine crash and nothing else, you need two events together, because neither is sufficient alone:

EventFires forCarries
handleStreamerDisconnected
(onStreamerDisconnected in the SDK)		 Only the app process stopping — crash, unexpected close, machine down. No text.
redirectingWithMessage
(onSessionEnding)		 Every session end, for any reason. A readable message.

So: the crash-specific event tells you it was a crash but gives you nothing to say; the reliable event gives you something to say but fires for everything. Combine them — set a flag when the crash event arrives, and when the session-ended event follows, show your crash message only if that flag is set.

Do not read the message text to work out what happened. It is written for a person and the wording can change. Use the events to decide what occurred, and the text only to show someone.

One thing that applies to all three

The session ends regardless

None of these callbacks can cancel or delay it. Whatever you show, design it around the session already being over — offer a way to start a new one, rather than anything that implies the old one might come back.

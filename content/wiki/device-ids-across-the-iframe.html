Your page and the stream are two different websites. Each one sees the same microphones under different ids — so an id your page collects means nothing inside the stream. This is why choosing a microphone takes two commands instead of one.

The two websites

An embedded stream always involves two sites. Throughout this page:

Which siteWhat it does
Your page your own domain — the page holding the <iframe> Shows your interface. Never touches the audio.
The stream connector.eagle3dstreaming.com — inside the iframe Captures the microphone and feeds it to your Unreal app over WebRTC.

The same microphone, two different ids

Labels are not a way round it. The human-readable name is the same string on both sides, so matching by name looks tempting. It is not reliable: labels are empty until the microphone has been granted, they are not unique — two identical headsets produce two identical names — and they change with the operating system's language. The id is the only dependable handle.

So the list has to come from the stream

If your page builds a dropdown from its own enumeration, it will offer a1b2c3…, send that across, and the stream will not recognise it. The only workable order is: ask the stream for its own ids, show those, send one back.

The commands

DirectionMessage
your page → the stream{ cmd: "getMicDevices" }
the stream → your page{ type: "micDevices", ok: true, devices: [{ deviceId, label, isActive }] }
your page → the stream{ cmd: "setMicDevice", deviceId: "<an id from micDevices>" }
the stream → your page{ type: "micDeviceChanged", ok: true, deviceId, label }
the stream → your page{ type: "micDeviceChanged", ok: false, error, message }

micDevices can also arrive unprompted, when a microphone is plugged in or removed. Treat it as "here is the current list", not only as the answer to a question you asked.

What the stream does with the id

Three steps, and the order of the last two matters more than it looks. 

// inside connector.eagle3dstreaming.com, never on your page
const stream   = await navigator.mediaDevices.getUserMedia({
                   audio: { deviceId: { exact: chosenId } }
                 });
const newTrack = stream.getAudioTracks()[0];

await sender.replaceTrack(newTrack);   // swap the outgoing track
oldTrack.stop();                        // stop the old one LAST

Stop the old track last, never first. Acquire, swap, then stop. Any other order means a device that has been unplugged since the list was built costs the viewer the microphone they still had.

Where the audio actually goes

This is why granting the microphone on your page is not enough on its own. Your page never carries the audio. The stream's own site has to be able to open the microphone, and a permission belongs to one origin at a time. If the list comes back empty, see Choose the microphone under When the permission is the problem.

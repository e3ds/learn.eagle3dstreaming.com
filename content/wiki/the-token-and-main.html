A stream starts with one call, e3ds_controller.main(), and that call needs a session token. Everything else in the Web SDK sits either side of those two facts. This page is both of them: where a token comes from, and what to do with it.

The one call that starts a stream

e3ds_controller.main({
    token:      tokenResponse.token,
    socket_url: tokenResponse.socket_url,
    client:     "your-username"
});

Both token and socket_url come back from the token API — they are two fields of one response. Anything else you pass is carried along and used where it applies.

Why you will not find socket_url in the sample

The sample never names it. requestSessionToken() returns the whole response and spreads it straight in: 

e3ds_controller.main({ ...tokenResponse, client: yourUserName });

Convenient, and it hides where the fields came from. They came from the API, in the response, and main() refuses without either of them — result.missing names whichever is absent.

main() is ours. startStream() is yours.

The sample has a function called startStream() in sdk-token.js. It fetches a token and then calls main(). It is convenience code you own — rename it, replace it, or delete it, and the SDK neither knows nor cares.

So wherever timing matters — "assign your callbacks before the stream starts" — the line meant is main().

Three ways to get a token

main() does not care where the token came from. Pick by how far along you are.

MethodGood forYour key lives
1By hand, from the Control Panel a first look, a test, a bug report — no code at all nowhere near your page
2The API, called from the browser building and developing — what the sample does in your page, readable by anyone
3The API, called from your server production on your server, where it belongs

Method 1 — by hand, from the Control Panel

No code, and no key in your page

The Developer section has a Token Generation tab. Generate one, paste it into main(), and you have a stream. 

e3ds_controller.main({
    token:      "the token you generated",
    socket_url: "the socket_url beside it",
    client:     "your-username"
});

No API call, no key anywhere in your page, one line of code. This is the quickest way to prove an integration works before any of the plumbing exists.

A token is single use and expires, so the one you generated for a test is spent afterwards and harmless.

Method 2 — the API, called from the browser

What the sample does; fine while building 
POST https://token.eagle3dstreaming.com/api/v2/token/create
Content-Type: application/json
Authorization: Auth <your Streaming API key>

The body says which application to launch, for whom, and for how long:

{
  "object": {
    "core": {
      "domain":            "connector.eagle3dstreaming.com",
      "userName":          "your-username",
      "appName":           "YourAppName",
      "configurationName": "your-configuration",
      "version":           "latest"
    },
    "configurationToOverride": {}
  },
  "expiry": 60000,
  "client": "your-username"
}

object.core is the application block from sdk-config.js, passed through as-is. expiry is how long the token stays valid in milliseconds — it only has to survive long enough to start the session.

The response is what main() wants:

{
  "token":      "…",
  "socket_url": "…"
}

This puts your key in the page

Fine while you are building and nobody else can reach it. Not fine the moment the page is public — the key is one click of View Source away and does not expire. Method 3 is the same request from somewhere the browser cannot read.

Read the body when it refuses

A 401 says the request was refused; the body says why — wrong key, expired, unknown application, quota. That sentence is the difference between fixing it and guessing, and it is easy to discard unread.

The commonest cause is the wrong credential entirely: the account API key instead of the Streaming API key. See Streaming API key and tokens.

Method 3 — the API, called from your server

Production. The only one where your key is not published

Exactly the same request as Method 2 — same endpoint, same header, same body. The only difference is who makes it: your server instead of the browser.

Your page asks your server, your server asks us, and only the token comes back to the browser: 

// in your page - no key anywhere
const tokenResponse = await fetch("/api/stream-token", { method: "POST" })
                                .then(r => r.json());

Your server holds the Streaming API key and makes the call from Method 2. The browser receives a token that expires in the time you set and is single use, so a leaked one is harmless — which a leaked key never is.

It is one function's worth of change: keeping your API key off the browser.

Putting it together

// 1. Get a token — by hand, from the API, or from your own server.
const tokenResponse = await fetch("/api/stream-token", { method: "POST" })
                                .then(r => r.json());

// 2. Register your callbacks BEFORE starting. Anything assigned after
//    main() has already missed whatever fired first.
e3ds_controller.callbacks.onSessionEnding = function (message) {
    showMyEndScreen(message);
};

// 3. Start.
e3ds_controller.main({
    token:      tokenResponse.token,
    socket_url: tokenResponse.socket_url,
    client:     "your-username"
});

One username, under three names — and they are the same thing

You will meet this value spelled three ways, and the inconsistency is ours, not yours:

  • clientUserName in sdk-config.js
  • client in the token request body and in main()
  • userName inside object.core

In practice you set all of them to the same value: your username. The one rule that matters is that the value used to create a token must be the value used with it afterwards — the token is looked up by it, so a mismatch answers 404 for a token that is perfectly good, which reads as expiry and is not.

We are collapsing these onto one name. Until that ships, send client to main() — it is what the published SDK reads, and the newer spelling will simply be ignored by a build that predates it.

The failure if you get ahead of it is unhelpfully disguised: the value reaches nothing, the token is then looked up by an empty one, and verification answers 404 for a token that is perfectly good — which reads as expiry.

A token is single use

Restarting a stream needs a fresh one — reusing the previous token fails. Fetch the replacement before tearing down the session that is running, so a failed request leaves the viewer watching what they already had rather than nothing at all.

It reports failure rather than throwing

A missing field is a setup mistake, not an exceptional condition, so main() returns instead of throwing — a throw would take down whatever called it. Check the result: result.ok === false, with result.missing naming exactly what was absent. The full shape is in the Web SDK reference.

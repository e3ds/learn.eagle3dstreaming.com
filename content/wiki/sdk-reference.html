What main() expects, and what it gives back

main(data) needs token and socket_url. Anything else on the object is carried along and used where it applies — client, for instance, identifies the viewer. A field your token endpoint starts returning is available to the player without any change here.

It returns rather than throws, so a setup mistake cannot take down the page that called it: 

const result = e3ds_controller.main(tokenData);

if (result && result.ok === false) {
    // result.missing  ->  ["token"]
    // result.message  ->  a sentence naming what is missing
    showYourOwnError(result.message);
}
Why this check is worth writing

A missing field used to produce a session that connected to nothing and a page that simply sat there — the mistake surfacing minutes later as "the stream does not work". It now says so immediately, in the return value and once in the console. The console line names the keys it received, never the values, because token is a credential.

setResolution() returns the same shape, so a bad size is visible rather than silently streamed: 

const r = e3ds_controller.setResolution(0, 1080);
// { ok: false, error: "invalid_resolution", message: "..." }

Restarting a stream

A token is good for one session only, so a restart means a fresh token. 

async function restartStream() {
    // Fetch the token BEFORE ending the session: if this fails, the viewer
    // keeps the stream they already had.
    const tokenData = await requestSessionToken();
    if (!tokenData) return;

    e3ds_controller.terminate();
    e3ds_controller.main(tokenData);
}

End the current session before calling main() again. main() initialises the player into #playerUI, so calling it while a session is running builds a second player on top of the first. The order above also matters the other way round: fetching the token first means a failed token request costs the viewer nothing, instead of ending a working stream and then failing to replace it.

Callbacks

Assign these to e3ds_controller.callbacks. All are optional — the ones you do not define are simply never called. Assign them before the stream starts, which is why session-token.js loads last in the sample.

Starting up

CallbackWhen it firesReceives
onConfigAcquireConfiguration received; the stream is not playing yet.—
onReceivingAppAcquiringProgressYour app is downloading onto the machine.percent (0–100)
onReceivingAppPreparationProgressThe downloaded app is being prepared.percent (0–100)
onReceivingAppStartingProgressThe app is launching.percent (0–100)

Downloading and preparing only happen when they are needed. A machine that already holds your app skips both, so a loading screen must not wait for progress that may never arrive. This is the same behaviour described in the session phases, seen from your code.

Running

CallbackWhen it firesReceives
onDataChannelOpenThe stream is live. Build your interface here.—

Ending

CallbackWhen it firesReceives
onRedirectingWithMessageAny reason the stream ends. Use this one.message
onStreamerDisconnectedOnly when the app itself crashed or stopped.—
onSessionExpiredThe session's time limit was reached.—
onRedirectingWithMessage is the dependable one

It fires for essentially every way a session ends — crash, idle timeout, expired session or link, wrong password — and gives you a short line of text for the visitor. The other two are narrower: onSessionExpired covers only the time limit, and onStreamerDisconnected only a genuine crash, and it can arrive too late to be useful. If you are showing one "session over" screen, build it on the first.

Show the message; do not parse it. Treat it as text for a person to read, not as a status code — the wording can change. Write it with textContent rather than innerHTML: it comes from the platform and is meant to be read, not executed.

The sample ships a working version in stream-callbacks.js that puts the message in a full-page overlay, so the demo shows something real instead of logging where nobody is looking. It is meant to be replaced — the block is marked THIS IS THE PART YOU REPLACE. Swap it for a screen your page already has: 

document.getElementById("myEndScreen").style.display = "flex";
document.getElementById("myEndMessage").textContent = message;

The stream ending cannot be cancelled from your page. Design your "session over" screen around the fact that it is happening regardless. Custom screens covers what to put there.
